# Модель данных календарного агента

## 1. Скриншот

Каждая загрузка скриншота фиксируется отдельной записью.

| Поле | Тип / смысл |
|---|---|
| `id` | Уникальный ID скриншота |
| `source_type` | Тип: `plan` или `fact` |
| `day_date` | Дата событий после подтверждения пользователем |
| `sent_at` | Дата и время отправки боту |
| `telegram_file_id` | ID файла в Telegram |
| `device_type` | Устройство: телефон, компьютер или неизвестно |
| `visible_from`, `visible_to` | Начало и конец видимого интервала по шкале времени |
| `covers_full_day` | Показывает ли скриншот весь день |
| `date_confirmed` | Подтвердил ли пользователь предложенную дату |

По умолчанию бот предлагает календарную дату отправки. Перед распознаванием и сохранением событий пользователь подтверждает её или указывает другую.

## 2. Распознанное событие

Каждая запись, распознанная на скриншоте, сохраняется отдельной строкой. Утренний план и вечерний факт не перезаписывают друг друга.

| Поле | Тип / смысл |
|---|---|
| `id` | Уникальный ID события |
| `screenshot_id` | Ссылка на скриншот-источник |
| `day_date` | Подтверждённая дата события |
| `source_type` | `plan` или `fact` |
| `task_name_raw` | Название задачи в исходном распознавании |
| `task_name_normalized` | Название для сопоставления |
| `start_time`, `end_time` | Начало и конец по левой шкале времени и высоте плашки |
| `duration_minutes` | Длительность в минутах |
| `label` | Метка календаря, если распознана |
| `color_hex` | Цвет плашки на скриншоте |
| `project_or_category` | Проект или категория по справочнику, если определяется |
| `visual_completion` | Визуальный статус плашки факта: `done`, `not_done` или `unknown` |
| `recognition_confidence` | Уверенность распознавания от 0 до 1 |
| `created_at` | Дата и время сохранения |

Для MVP нормализованное название строится в приложении: Unicode NFC, удаление пробелов по краям, сведение повторных пробелов к одному и приведение регистра без изменения слов и знаков препинания. Пунктуация и смысл названия сохраняются.

## 3. Результат сверки

После распознавания всего скриншота «факт» система сверяет наборы событий за одну дату. Отдельная строка результата связывает плановую запись с фактической или фиксирует отсутствие одной из сторон.

| Поле | Тип / смысл |
|---|---|
| `id` | Уникальный ID результата |
| `day_date` | Дата сравниваемого дня |
| `plan_event_id` | Ссылка на задачу плана; пусто для дела вне плана |
| `fact_event_id` | Ссылка на задачу факта; пусто, если плановая задача не найдена |
| `result` | Итог: `done`, `partially_done`, `not_done`, `outside_plan`, `unconfirmed` или `uncertain` |
| `match_method` | Для пары — `exact_normalized_title`; для одиночной записи пусто |
| `reason` | Краткое основание результата |
| `created_at` | Дата и время формирования результата |

## 4. Правила сопоставления и статусов

1. Сначала все события скриншота «факт» сохраняются отдельно. Затем сверяется полный распознанный набор с планом за ту же дату.
2. Единственный критерий связи — точное совпадение нормализованного названия задачи. Время, длительность, цвет и проект при поиске пары не участвуют.
3. Для MVP принято допущение, что названия задач не повторяются в пределах дня в каждом наборе «план» и «факт». Если это условие нарушено или распознавание названия неуверенное, результат — `uncertain`, автоматическую пару не создавать.
4. Совпавшая задача с осветлённой плашкой факта получает результат `done`.
5. Совпавшая задача, плашка которой в факте сохранила исходный цвет плана, получает результат `partially_done`: задача выполнена частично и перенесена для завершения на другой день.
6. Плановая задача без пары в факте получает результат `not_done`, если соответствующее время видно на скриншоте факта или скриншот охватывает весь день. Если нужное время не попало в изображение, результат — `unconfirmed`.
7. Фактическая задача без пары в плане получает результат `outside_plan`.
8. Каждая плановая запись и каждая фактическая запись участвует не более чем в одной паре. Несопоставленные записи также получают отдельные строки результата.
9. Цвет и проект используются для описания и определения статуса, но не для установления связи между задачами.

## 5. SQLite-файл

SQL-реализация структуры находится в `sql/schema.sql`. База будет размещена на Linux VPS Beget. Сам файл схемы — инструкция создания таблиц, а не уже созданная и работающая база данных.
